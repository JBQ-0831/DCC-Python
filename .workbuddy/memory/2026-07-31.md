## git 提交踩坑：WorkBuddy 沙箱拦截 ref 的 lock+rename（16:44 续）
- 沙箱里 `git checkout -b` / `git commit` / `git update-ref` 都是"假成功"：commit 对象能写进 `.git/objects/`（fsck 可见 dangling commit），HEAD 文件能写，但 `.git/refs/heads/` 下分支文件写不进去——git 用 lock 文件 + rename 原子提交，沙箱拦了 rename / 在 `.git/refs` 下创建。结果：commit 变 dangling、`git branch` 看不到、`git rev-parse HEAD` 报 unknown revision。
- 诊断命令：`git fsck --no-reflogs | grep dangling`、`cat .git/HEAD`、`ls .git/refs/heads/`、`git cat-file -t <sha>`。验证 `.git/refs/heads/` 目录本身可写（`touch` 成功），确认是 git 的 lock+rename 机制被拦，而非目录不可写。
- 修复手法（绕过 git ref 后端）：① 手工写 `.git/refs/heads/<branch>` 内容为 commit SHA（创建 loose ref）把悬空 commit 挂回分支；② 若 commit 因 checkout 异常成 root-commit（无 parent），用 `git commit-tree <tree> -p <main-sha> -m ...` 重建带 parent 的 commit 对象，再手工写 ref 指向它，使历史与 main 连贯。
- 已交付：`feat/py2-dcc-support` 分支，commit `1c04ed3`（parent=a9b11a8，112 文件 / 18543 行）。未 push（开发中的代码只本地提交）。排除 `.workbuddy/`、`_pytest_tmp.log`、`overview.md`。
- ⚠️ 风险：该沙箱内 git 分支 ref 更新不可靠，后续再 commit/切分支/merge 可能再卡，需同样手工修 ref 或在本机真实环境操作。push 前建议本机确认分支状态。
